# Unify 统一记忆层：架构与交互设计

2026-11-22 · 由本次对话与本机 Codex（`codex-cli 0.171.0` / `gpt-6.2-astra`，high）联合评审定案

## 摘要

**结论：Unify 不做重型私有向量记忆（黑盒召回 / 独立数据库），而是建设一层薄而克制的「显式分层统一记忆层（Unified Memory Layer）」。**

整套方案围绕四个核心决策展开，并在设计上严格满足 **Prefix / KV Cache 友好** 与 **跨平台（含无软链权限 Windows）可靠运行**：

1. **Phase 1（API 记忆补齐）**：以轻量、有界的显式选源 resolver 为 `text-only` API 模型（DeepSeek、OpenAI、自定义端点等）注入确定性分层记忆；确立「普通续问继承当前分支记忆版本、精确重试回放原调用不可变快照」两条硬契约。
2. **KV Cache 友好改造**：API 对话升级为 append-only 结构化 `messages`；汇总 prompt 固定裁决原则前置；补齐缓存 token 读写观测，以实测为准。
3. **Phase 2（跨工具 SSOT 与同步）**：原生共读同一文件时零写入；需要同步到异名文件时，采用「显式预览 + 边界清晰的托管区块」单向同步，软链仅作主动勾选的高级选项。
4. **Phase 3（沉淀记忆交互）**：采用「卡片摘录为主 + 按需提炼为辅」；点击保存**立即写盘**（不引入“待应用”隐形队列），同时借鉴 Claude Code / OpenCode 的做法——对 Unify 控制的 API 会话保持 `SessionStart` 头部快照冻结，若用户希望本对话后续立即遵循则通过**尾部 Append-Only `<memory-update>` 增量**生效，对原生 CLI 如实提示下轮自动读取。

## 现状评估

Unify 当前已具备多工具记忆扫描、编辑、备份恢复与分层管理界面（`src/memory/*`、`assets/memory.html`、`src/tui/memory.ts`），以及基于模型自报的记忆引用收集（`src/memory/report.ts`）。但在多模型并行对比、汇总与实施的主链路中，仍有五类明显断点：

| 环节 | 现状 | 问题 |
| --- | --- | --- |
| 多模型上下文对称性 | Claude / Codex 各自读取原生记忆文件；`text-only` API 仅通过 `src/core/context.ts` 注入提问中 `@path` 引用的本地文件 | API 模型几乎处于「失忆」状态参与对比，容易与 CLI 模型产生因背景缺失导致的假分歧 |
| 记忆扫描与热路径耦合 | `src/memory/scan.ts` 面向管理页面，会递归扫描子目录并同步执行 `git blame` | 不能直接把 `effectiveContext()` 接入提问热路径，且 `effectiveContext()` 未反映自动记忆截断与项目字节上限 |
| KV Cache 连续性 | `src/core/synth.ts` 首轮纯文本、次轮切换为 JSON 历史字符串；`context.ts` 将本轮 `@file` 拼在历史之前；汇总 prompt 将固定原则放在动态回答之后；`Usage` 未采集缓存命中字段 | 多轮追问和汇总都会破坏前缀复用，且缺少可观测指标验证缓存收益 |
| 重试语义与快照 | `src/core/workflow.ts` 重试时克隆 `record.input`，但仍对当前磁盘重跑 `resolveSharedFileContext()` | 若中途修改了记忆或附件，重试同一问题的两个结果失去可比性 |
| 决策沉淀与跨工具同步 | 汇总共识与实施结论留在 `.unify/runs/`；Windows 非管理员下 `symlinkSync()` 会触发 `EPERM` | 高价值架构共识难以回流为持久约定；跨工具共享不能把软链作为默认实现 |

## Phase 1：面向 `text-only` API 的分层记忆注入

### 1.1 记忆来源发现：有界、轻量、显式选源

| 候选项 | 评审结论 |
| --- | --- |
| 直接复用某个 harness 的 `effectiveContext()` | **不采用。** 会引入同步 `git blame` 和子目录遍历，且可能把 Claude 自动记忆、本地私有文件、组织策略或递归 `@import` 意外披露给外部端点 |
| 强制使用 `~/.unify/memory.md` + `.unify/memory.md` | **不作为默认。** 已有 `AGENTS.md` 的团队会被迫维护两份规则；且仓库 `.gitignore` 通常忽略 `.unify/`，导致项目共享规则无法进 Git |
| **有界发现 + 显式选源** | **采用。** 零自动创建、热路径轻量只读、边界透明 |

具体规则：

- **用户层**：仅当用户主动启用共享个人记忆时读取（如 `~/.unify/memory.md` 或用户显式指定的个人文件）。**按实际目标端点控制披露权限**（因为用户配置可以覆盖同名 provider 指向自建端点，仅信任用户配置中的授权，沿用 `src/core/config.ts` 的 `mergeConfig()` 安全边界）。
- **项目层**：从仓库根（`.git` 所在目录）逐级向下到当前 `cwd`，每级最多选一个共享源。默认识别 `AGENTS.md`；若目录中仅有 `CLAUDE.md`，提供一次可记住的选择；两者并存时显式展示实际选中项，并允许项目配置固定其一；`.unify/memory.md` 仅作可选主源。空项目不创建任何文件。
- **默认排除项**：首版只注入选中源的 Markdown 正文，默认排除原生自动记忆、`*.local.md`、组织策略、带 `paths:` 的条件规则和递归 `@import`；若选中源内存在未展开的 `@import`，在界面中给出可见提示。
- **确定性序列化**：新增轻量 resolver，只读选中文件；固定顺序为「用户层 → 项目根 → 各级子目录」，使用稳定的逻辑路径（不复用 `scan.ts` 中相对 `cwd` 且会截断长段名的 `display` 串）、统一换行、按 `realpath` 去重、按确定字节预算截断；截断、跳过、缺失均记录在本地调用清单中。
- **差异可见**：当同目录存在 `AGENTS.override.md` 等仅特定 CLI 读取的文件，或某外部端点无权接收个人层时，比较视图显式标注上下文差异；匿名汇总仅传递「是否有共享约定 / 附件 / 工具实读证据」，绝不向匿名标签泄漏路径或模型名。

### 1.2 调用链改造与硬契约

确立两条不可破坏的产品契约：
- **普通续问**：继承当前会话分支（`sessionId`）在 `SessionStart` 锁定的记忆版本。
- **精确重试**：回放原调用实际发送的不可变输入快照（记忆 + 附件 + 消息边界）；「按当前最新文件重新提问」作为独立语义的新调用。

改造范围：

1. **统一调用准备**：在 `workflow.ts` 的 `Journal.prepare()` 阶段产出完整输入，透传至 `orchestrator.ts`（`fanOut` / `runOne`）和 `providers/custom.ts`（`official.ts` 复用同一适配器）。保留 CLI 的纯文本 `prompt`，为 OpenAI 兼容 API 增加有类型的 `messages`；保留自定义配置的 `c.system` 且确保与共享记忆之间有固定分隔边界。模型连通性测试与自定义 `command` 目标不自动注入个人记忆。
2. **覆盖全部角色**：API 答题与 API 汇总（含独立配置的汇总器、不可用回退得到的汇总器、同时答题并汇总的目标）均使用同一版本的共享记忆与本轮附件，仅各自保留对应的任务说明；`decider` 首版维持现有紧凑路由契约；CLI 实施继续走原生加载并记录 `planSource`。
3. **快照持久化与隐私隔离**：同步更新 `src/core/store.ts` 的读写 Zod schema 与老记录兼容逻辑。run 内记录记忆版本、层清单、逻辑路径、内容摘要及每次调用的快照引用，正文按内容哈希去重存储；**个人层记忆正文存放在用户私有快照目录，不写入项目 `.unify/runs/`**，也不复制到每张卡片的 Markdown 导出中；若私有快照已被清理，精确重试明确提示快照缺失而非静默改读现盘。
4. **记忆引用汇报（`report.ts`）**：对实际收到记忆注入的 `text-only` API 答题与汇总同样启用 `requestMemoryReport`。将流式解析器 `collectMemoryReport` 改为显式接收 marker（不再仅依赖 `prompt.endsWith(tag)`）。UI 严格区分：
   - **已注入（Unify 记录，可核验）**：来自调用快照的真实文件清单；
   - **模型自报采用**：来自 `memoryReferences`，可与快照路径/条目交叉核对，未匹配项标明「未核对」。

## KV Cache 友好架构与可观测性

### 2.1 前缀布局规范

KV Cache（Prefix Caching）依赖从请求头部开始的严格字节级前缀匹配。所有 API 调用必须遵循**变动频率由低到高**的层次排列：

```text
[1] System（最稳，SessionStart 冻结）：
    固定系统角色说明（c.system / 汇总裁决原则）
    → 静态分层记忆（用户层 → 项目根 → 子目录，固定逻辑路径与排序）
[2] History（Append-Only）：
    已确认的公共对话消息流 [U1, A1_public, U2, A2_public, ...]
    （U1 保留当轮实际发送的附件与问题，A_public 以分支选定的公共回答为准）
[3] Current Turn（最动，放末尾）：
    可选的一条会话内尾部增量 <memory-update>（仅在当前会话中途存记忆且启用本会话生效时）
    → 本轮动态 @file 附带文件
    → 本轮用户问题
    → 可选的记忆汇报尾注标记 <unify-memory-id>
```

严格禁止项：
- **禁止**在 `System` 前缀中放入当前时间、随机 ID、`runId`、Git 作者、同步状态或「整包总 hash」（否则仅改最后一个子目录文件就会从首行失配）。
- **禁止**把动态 `@file` 拼在历史对话之前（修正 `src/core/context.ts` 的 `attachContextToPrompt`）。
- **禁止**在汇总 prompt 中把固定原则放在动态 `<answer>` 之后（调整 `src/core/synth.ts` 的 `buildSynthesisPrompt` 顺序；每次新汇总照常洗牌匿名答案，复现同一评审输入时复用已存顺序与标签）。
- **禁止**首轮纯文本、次轮改成 JSON 字符串的格式翻转（API 目标自首轮起统一使用结构化 `messages`；上下文触顶时显式建立新基线，避免每轮滚动裁头导致持续失配）。

### 2.2 各链路实际缓存预期与观测补齐

不同 provider 的缓存能力差异很大，不能一概承诺同等节省：

| 链路 | 实际行为与缓存预期 |
| --- | --- |
| **DeepSeek 官方 API** | 默认开启上下文缓存并直接返回 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`，是最优先的实测验证端点 |
| **OpenAI 官方 API** | 稳定前缀有自动缓存收益（受模型最小长度阈值与保留时间限制），以响应中的 `cached_tokens` 实测为准 |
| **Anthropic（当前走 OpenAI 兼容层）** | Anthropic 官方明确其 OpenAI 兼容层不支持 prompt caching；当前改造先带来**上下文一致性收益**，若需缓存需后续评估直连 Messages API |
| **Gemini API / 自定义网关** | 取决于模型隐式缓存门槛或网关（vLLM/SGLang 等）配置，分别记账 |
| **Claude Code / Codex** | 当前每轮新启无状态进程（`--no-session-persistence` / `--ephemeral`），静态原生前缀可由各 CLI 服务端自行命中，但工具集、模式切换（ask → exec）和内部工具回合均由原生 harness 控制，不以 Unify 的 `sessionId` 承诺跨轮缓存连续性 |

**观测先行**：在 `src/core/types.ts` 的 `Usage`、`src/providers/custom.ts` 的 SSE schema 及各适配器中补齐缓存读写字段（如 `cachedInputTokens` / `cacheWriteTokens`，服务端未返回时显示「未知」），用实测数据验证收益。

## Phase 2：跨工具单一事实源（SSOT）与显式单向同步

采用 **「零写入优先 → 显式单向托管区块 → 软链仅作可选」** 三级策略，彻底规避 Windows 非管理员环境下 `symlinkSync` 的 `EPERM` 问题，且不破坏用户手写内容：

1. **原生共读同一文件 → 零写入**：例如多工具均读取同一份 `AGENTS.md`，或已存在指向同一真实文件的软链，直接识别为共享并展示实际读取该文件的工具列表（同时检测 `AGENTS.override.md` 遮蔽或条件规则）。支持原生 `@import` 且语义适合的目标，可预览添加一行相对引用而非复制正文。
2. **异名文件同步 → 显式「预览同步」+ 托管区块**：
   - 用户显式指定主源、目标工具与具体层，界面展示逐文件 diff 后才执行，**首版不做后台 watcher 和双向自动回写**。
   - 目标文件中仅操作边界明确的托管区块（例如成对注释标记），**区块外的手写内容按精确区段替换逐字节保留**（不复用会改写空白行的 `appendEntry()`）。
   - 记录上次同步时的「源摘要」与「目标区块摘要」：源变而目标块未变时安全单向更新；目标块被手改、标记损坏/重复或文件被 override 遮蔽时停在该文件并给出原因。连续执行两次同步保证第二次零 diff。
3. **软链 → 仅作显式高级选项**：仅当全文件完全等价且用户主动勾选时尝试创建；遇到 `EPERM` 明确报错并引导改用托管区块，**绝不静默降级为整文件覆盖**。
4. **写入安全补强**：将可选 `.unify/memory.md` 注册进可写槽位；校验 `realpath` 与父目录防止跨边界写盘或源/目标指向同一真实文件；多目标同步串行执行、写前复核 `baseHash`、按文件回报结果，确保部分失败可安全重试。

## Phase 3：「沉淀记忆（存为记忆…）」交互设计

### 3.1 模式选择

| 方案 | 体验与代价 | 结论 |
| --- | --- | --- |
| 每轮结束后自动调模型提议 / 待办收件箱 | 容易把未采纳路线、一次性操作和模型误判堆成噪音 | **不采用** |
| **卡片摘录为主 + 按需提炼为辅** | 零默认打扰、零默认额外开销、来源精确、长文本时再按需一键提炼 | **采用** |

### 3.2 完整交互流程（Desktop / TUI / CLI 共用核心服务）

1. **统一克制的入口**
   - **Desktop（`desktop/src/renderer/Thread.tsx`）**：在所有成功完成的「回答 / 汇总 / 实施」卡片底部 `footer` 放次级动作 **`存为记忆…`**，同时支持在正文中先划选片段再触发。仅在本轮结束且卡片有成功正文时启用（部分失败轮次仍可选成功卡）。点「沿用」或「实施」不隐含存记忆。
   - **TUI**：聚焦目标结果面板执行 `/distill`（后端按 ID 回读原结果，避免把界面拼接的自报区块误当正文）。
   - **CLI**：`unify memory distill --turn <id> --call <runId>`，默认仅输出目标、来源与 diff，显式加 `--apply` 落盘。
2. **轻量审阅面板（默认直接编辑，按需才调模型）**
   - 有划选片段时原样带入编辑框；整卡进入时，回答带入正文供选、汇总默认定位到 `## 最终答案`（`extractFinalPlan`）、实施并列展示「采纳的方案」与「实施回报」（不自动将模型自称“已完成”升格为已验证事实）。
   - 面板内提供可选按钮 **`提炼候选`**：仅在用户点击后独立调用指定模型，**不进入主对话 `historyAfter()`**，输入限定为原问题、选中材料和来源类型（默认排除 `reasoning`、工具日志、其他模型回答和个人记忆全文）。模型只返回最多 3 条候选规则、建议范围与原句摘录，不能决定写入路径；用户可逐条编辑、勾选或放弃，取消后仍可手工保存。
3. **同屏选层、查重与冲突处理**
   - 默认定位到当前项目主源，清晰展示实际路径、归属小节与受影响的工具列表；写入「个人·全局层」需用户主动切换。
   - 补齐**短中文规则的精确去重**（不局限于 `scan.ts` 当前 `>=16` 字符的检测），精确重复直接高亮定位；相似或潜在冲突条目并排展示，提供「跳过 / 追加 / 替换原条」。保存时强制携带预览时的 `baseHash`，磁盘冲突则刷新重展 diff。
4. **干净正文 + 本地溯源**
   - 写入 Markdown 的仅是用户审阅后的干净条目，不向正文插入机器注释污染文件。
   - 溯源元数据（`turnId`、`runId`、`scope`、原始匿名 `[ref:N]` 与标签映射、实施关联的 `planSource`、原文摘录、写入前后摘要）保存在 Unify 本地审计记录中，并在记忆管理页支持回查来源；若团队需要跨机器共享溯源，可显式选择提交配套记录。
5. **保存与生效边界（对齐主流 Harness 最佳实践）**
   - **点击确认一律立即写盘**，不设隐藏的「待应用队列」，确保磁盘文件与记忆管理页、外部编辑器始终一致。
   - **API 会话（Unify 控制消息流）**：遵循「`SessionStart` 冻结头部 + 尾部 Append-Only 增量」策略——保存后**不改动当前 session 顶部的静态 `system` 记忆**（零 KV Cache 破坏）；默认提示「已写入，新对话自动生效」，并提供可选开关/动作**「本对话后续也生效」**——勾选后仅在下一轮 `user` 消息侧尾部追加一条一次性的 `<memory-update>`，既立刻遵守新规则，又完整保留前面所有历史前缀缓存。
   - **原生 CLI**：状态文案如实提示「已写入磁盘；原生 CLI 将在下轮自动读取最新文件」。

## 分阶段实施与验收门槛
