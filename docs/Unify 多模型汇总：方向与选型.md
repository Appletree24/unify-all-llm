# Unify 多模型汇总：方向与选型

Nov 21, 2026 · @Appletree24

## 摘要

**建议：Unify 的汇总改为帮用户做选择，不再替用户写一份「最好的答案」。** 汇总模型的角色从裁判改为分析员：按方案分组、拆开分歧、保留少数意见。用户的选择是唯一依据，同时用于实施和后续对话。

依据是 2025—2026 年研究的三个共同发现：

- 瓶颈在评判者，而不在候选数量。
- 不同模型的错误高度相关，所以多数一致不等于正确。
- 融合并不总是优于选择。

这个方向由 Claude 的调研和 Codex（gpt-6.2-astra，ultra 档）的独立回答合并而来，双方结论一致。默认策略还需要用「评估方案」一节的离线评估来确定。

## 现状评估

**骨架方向正确，问题在汇总结果怎样被下游使用，以及只有一种汇总策略。** 现在的流程是：成功的回答打乱顺序、匿名成 `[ref:N]`，由一个模型按「共识 / 分歧 / 独有亮点 / 最终答案」写一整段 Markdown。这段文本同时用于界面展示、实施的 `final_plan` 和后续对话的历史。

| 环节 | 值得保留 | 问题 |
| --- | --- | --- |
| 独立回答与匿名 | 各模型独立作答；匿名加打乱顺序；原答、编号映射和调用记录都能回查 | CLI 目标读了仓库，API 目标只看到提问，证据条件不同。匿名能隐藏模型名，但不能让几份回答成为相互独立的佐证 |
| 汇总提示 | 要求列出分歧、不默认多数正确、鼓励核实代码 | 同一份提示又要它裁定谁对，并写出比所有候选都好的答案。事实分歧可以查证，偏好取舍却只能由用户决定 |
| 路由（decider） | 可选；用户手选优先；有效回答少于两个时跳过汇总 | 在看到回答之前就决定要不要汇总，无法知道候选之间是重复、互补还是冲突 |
| 汇总目标回退 | 保证流程能走完 | 回退到第一个成功的答题者，它的自我偏好和能否核查都没有考虑，记录里也没有标注 |
| 实施来源 | 实施需要确认；能追溯到具体轮次和调用 | 交给执行模型的是整篇评审，包括被否决的意见；`[ref:N]` 原样传过去 |
| 跨轮历史 | 有历史，追问能接上上下文 | `historyAfter` 优先使用汇总。用户选了 B 去实施，后续追问仍然沿用推荐 A 的汇总；本轮的 `[ref:1]` 还会和下一轮的 `[ref:1]` 撞在一起 |

最优先的问题是**用户的决定在实施记录和后续对话里不一致**，这个问题由 Codex 指出。

## 研究与实践依据

**结论：多模型汇总的收益取决于评判者是否够强，而不是候选有多丰富。** 下表按主题归纳。「性质」列标出是同行评审、预印本还是产品或博客。大部分内容来自摘要和会议页面，没有逐篇读全文。

| 主题 | 来源 | 性质 | 发现 | 对 Unify 的含义 |
| --- | --- | --- | --- | --- |
| 融合占优 | [Fusion-of-N](https://www.arxiv.org/pdf/2510.00931)、[GSA](https://arxiv.org/html/2503.04104v2) | ICLR 2026 | 开放生成任务上，融合稳定好于选出一个；Fusion-of-N 的实验用的是同一模型多次采样 | 调研和写作类题目可以保留融合 |
| 选择占优 | [When Agents Disagree](https://arxiv.org/html/2603.20324v1)、[DeliberationBench](https://arxiv.org/html/2601.08835v1) | 预印本 2026 | 选择在 42 个任务上全部胜出；融合有 80% 以上输给单模型。提出「选择瓶颈」：评判者质量低于阈值时，多样性反而有害 | 融合还是选择存在争议，要靠评估决定 |
| 混合不同模型 | [Self-MoA](https://arxiv.org/abs/2502.00674) | TMLR 2026 | 只用最强的单个模型多次采样，大多数情况下优于混合不同模型 | 「强单模型多采样」要列为基线 |
| 相关错误 | [Correlated Errors](https://proceedings.mlr.press/v267/kim25e.html) | ICML 2025 | 在其中一个数据集上，两个模型都答错时，约 60% 给出相同错答 | 「三家都同意」不能换算成正确率 |
| 相关错误 | [Nine Judges, Two Effective Votes](https://machinelearning.apple.com/research/correlated-llm-evaluation-panels) | NeurIPS 2026 | 9 个评委只相当于约 2 票独立意见；最好的单个评委能追平整个评审团 | 「共识」一节可能给用户虚假的安全感 |
| 相关错误 | [LLMs as a Jury](https://arxiv.org/pdf/2607.10139) | 预印本 2026 | 错误互不相关时，一致性可以当作验证器；各模型共享同一个误解时，全票一致也是错的 | 同一家族、同样证据的共识要降权 |
| 少数派 | [Minority Sentinel](https://arxiv.org/pdf/2606.29270) | 预印本 2026 | 2:1 分歧时，少数派正确的比例约 25%；让 LLM 当裁判去推翻多数，效果反而变差 | 汇总模型不应当裁判；少数意见保留原文 |
| 评审偏差 | [Self- and Other-Labels](https://aclanthology.org/2026.findings-emnlp.1571/) | EMNLP 2026 Findings | 内容质量相同时，标注「你写的」或「别人写的」会双向推动评分，10 个评委全部如此 | 匿名有实际作用；提示词里不能暗示作者身份 |
| 评审偏差 | [Are LLM Evaluators Really Narcissists?](https://proceedings.mlr.press/v306/roytburg26a.html) | ICML 2026 | 此前「自我偏好」的结论只有 51% 经得住对照检验；偏爱自己主要发生在它自己答错时 | 汇总模型最好不在答题者里，但不必过度设计 |
| 评审偏差 | [CodeJudgeBench](https://preview.aclanthology.org/ingest-acl/2026.acl-long.888/) | ACL 2026 | 26 个代码裁判模型的判断都有显著随机性 | 单轮裁决不足以保证正确 |
| 加权聚合 | [Beyond Majority Voting](https://proceedings.mlr.press/v306/ai26d.html)、[A Jury, Not an Electorate](https://arxiv.org/pdf/2610.21085) | ICML 2026；预印本 | 用历史准确率和模型间相关性加权，优于多数投票；也可以从无标注答案估计可信度 | 可以用 `.unify/runs/` 的历史估计每个模型的可信度 |
| 路由 | [PISA-E](https://arxiv.org/pdf/2611.10193) | 预印本 2026.11 | 按问题内容和成本偏好，动态决定调用哪些模型、调用几个 | decider 可以从「要不要汇总」扩展到「用哪些模型」 |
| 代码选择 | [CodeMonkeys](https://arxiv.org/abs/2501.14723)、[TestGRAD](https://arxiv.org/pdf/2610.10242)、[SWE-Lego](https://arxiv.org/pdf/2601.01426) | 预印本 | SWE-bench 上生成多个补丁，用测试或验证器挑选，而不是融合 | 实施类问题用「选择加验证」 |
| 产品 | [Perplexity Model Council](https://www.gend.co/blog/perplexity-model-council) | 产品 2026.2 | 3 个模型独立回答，汇总成一致、分歧、独有观点的表格，定位是辅助决策 | 和 Unify 现在的四节结构几乎一样 |
| 产品 | [OpenRouter Fusion](https://openrouter.ai/docs/guides/routing/routers/fusion-router) | 产品文档 | 分析模型只对比不合并，列出共识、分歧、部分覆盖、独有观点和盲区，最后由调用方的模型写答案 | 「分析员」分工的现成参考 |
| 产品 | [Cursor 3 best-of-n](https://www.agentpatterns.ai/tools/cursor/agents-window/) | 产品（二手介绍） | 每个模型在独立 worktree 里完成同一任务，并排展示由用户选；官方论坛 2026 年 4 月说多模型选择器已撤下 | 「隔离实施后再比较」可作为独立模式 |
| 开源 | [karpathy/llm-council](https://github.com/karpathy/llm-council) 及衍生项目 | 开源 | 回答 → 匿名互评排序 → 主席汇总；衍生项目里有的编排多个 CLI，有的强调保留少数意见 | 互评成本是 N² 量级，不宜作为默认 |
| 交互 | [LLMartini](https://arxiv.org/html/2510.19252) | 预印本，18 人研究 | 回答按语义对齐成片段，一致内容自动合并，差异用颜色标出，各项指标优于手动比较 | 汇总可以做对齐和对比，不必做裁决 |
| 交互 | [Sensemaking in Multi-Agent LLM Interfaces](https://dl.acm.org/doi/10.1145/3772318.3791157) | CHI 2026 | 展示各自理由有助于用户自主判断，但用户仍倾向于跟着多数走；展示互相批评会提高信任 | 要防止用户过度信任「共识」 |

## 推荐方向

**定位：服务需要在真实项目里做决定的人，用户的选择是最终依据。** 在自己的项目里，带着仓库上下文的用户很可能是最强的评判者，这正好绕开「选择瓶颈」。

### 流程

各模型先独立回答，**看过回答之后再分流**：先判断候选之间是重复、互补还是冲突，再决定走哪条路。看回答前的 decider 仍然保留，用来决定调用哪些模型。

&#91;embedded content: 推荐流程 · 五条分流路线，一个反馈循环\]

五条路线都汇到「用户选定」；决策记录同时用于实施和后续对话，并通过反馈循环影响下一轮选模型。

| 任务与条件 | 路线 | 主要取舍 |
| --- | --- | --- |
| 简单问题，或一个能读仓库的目标就能查明的事实 | 单模型回答或查证；用户明确要求多模型时尊重选择 | 延迟和额度最低，少一次发现遗漏的机会 |
| 架构选型、改造计划 | 独立提案 → 按决策点比较 → 用户选定 | 最契合实施入口；质量取决于能否准确保留前提和少数意见 |
| 调研、说明文，各回答的贡献能兼容 | 融合成一篇，重要结论保留出处；汇总者自己的推断单独标明 | 便于阅读；要防止丢掉限定条件，或把互斥建议拼在一起 |
| 只剩一个会改变结论的事实争议 | 定向查证：文件、官方资料、已有测试 | 额外调用有明确目的；证据不足时保留争议 |
| 效果只能靠运行判断，且用户接受成本 | 隔离实施后比较补丁和验收结果（独立模式） | 证据最接近交付物；成本高，改变了「先选后做」 |

### 汇总模型：分析员，不是裁判

- 按做法分组，合并只是措辞不同的回答；比较的是「方案」，不是给「模型」排名次。
- 每个方案写清适用条件、代价、风险和验收方式，并能链回原答。
- 分歧拆成两类：事实分歧交给能读仓库的目标去查证；偏好取舍交给用户。
- 少数意见保留原文，不被改写掉。
- 「共识」标注「不代表正确」，尤其是几个模型来自同一家族，或看到的证据相同时。
- 标出每个回答依据了哪些证据，比如读过哪些文件。
- 可以给一句有条件的推荐，并说明什么事实或偏好会让推荐反过来。
- 汇总模型优先选不在答题者里的；做不到时在记录里标出来。提示词里不暗示作者身份。

### 决策记录

用户选定后，生成一份决策记录：采纳了什么、有哪些约束、还有哪些待验证的假设、怎样验收。交给执行模型的是这份记录，不是整篇评审。后续对话的历史也使用它，并把 `[ref:N]` 换成模型名。如果用户采纳 A 的主体、再加上 B 的局部建议，要把新增内容及其兼容条件列出来。

### 反馈循环

`.unify/runs/` 里的实施记录（`planSource`）已经记着用户选了哪个回答去实施。再加上验收结果，就能估计每个模型在这个项目、这类问题上的可信度，反过来用于 decider 选模型和给回答加权。现成工具里很少有人这样做，可以成为 Unify 的差异点。

## 备选方向

**三个备选方向都可行，但各自优化的目标不同。** 选哪个，取决于「待作者回答的问题」里第 1 题的答案。

| 方向 | 优化目标 | 适合 | 代价与风险 |
| --- | --- | --- | --- |
| 保持融合为默认（现状改良） | 一份可直接读的成稿 | 主要用户只想拿到答案 | 有研究显示融合会丢掉更好的那个回答；分歧仍由汇总模型一个人拍板 |
| 引入互评或辩论（llm-council 式） | 通过互相批评提高质量 | 出错代价很高、额度充足 | 成本是 N² 量级；[Debate or Vote](https://arxiv.org/abs/2508.17536v1) 发现辩论的收益主要来自投票，而不是讨论本身 |
| 强单模型多采样（Self-MoA 式） | 答案准确率 | 只关心正确率、不需要多种视角 | 失去多厂商的视角和分歧信息，与 Unify 「并排比较」的定位冲突 |

推荐方向并不排斥这三者：融合保留给调研类题目，互评可以作为高代价问题的可选升级，强单模型多采样作为评估基线。

## 评估方案

**默认策略应由离线评估决定，不凭印象。** 从 `.unify/runs/` 取一批真实问题，脱敏后按事实核查、架构取舍、开放长答、可验收实施四类分组。

两组对照分别回答两个问题：

1. **怎样汇总**：在同一批候选上，比较现有四段汇总、结构化方案比较、直接选一份原答。
2. **是否值得多问模型**：在接近的额度下，比较强单模型、同模型多采样、跨模型组合。

| 指标 | 衡量什么 |
| --- | --- |
| 做出选择用时 | 用户从看到结果到选定方案花了多久 |
| 少数意见保留率 | 只有一份回答提到的关键观点和原文依据，在汇总里保留了多少 |
| 首次验收通过率 | 选定方案实施后一次通过验收，还是需要返工 |
| 成本与延迟 | 每题的 token、额度和端到端用时 |
| 选择者强度 | 用户或汇总模型挑中最佳候选的比例，对应「选择瓶颈」是否成立 |

实施对照尽量固定仓库版本、执行模型和验收条件。如果结构化比较只在架构题上节省时间，就只在架构题上把它设为默认。

## 待作者回答的问题（已拍板 · 2026-11-22）

以下 5 个问题已由作者确定方向，用于定稿 P0/P1 实现方案：

- [x] **首要用户和成功标准是什么？** 面向**日常通用使用场景**，兼顾直接拿高质量答案与复杂问题对比决策，不强行要求每轮手工选定。
- [x] **实际问题的构成大致如何？** 通用日常 Harness，不绑定单一垂直领域（日常问答、调研、写作、排错、改代码混合出现）。
- [x] **愿意把多少决定交给汇总模型？** 采用**自适应高质量综合器**：互补信息直接融合出完整成稿；客观事实分歧能核实则直接查证裁定、否则标为未核实；真正互斥的路线/偏好分歧不硬缝合，按方案拆开并给带反转条件的有条件推荐，同时保留少数派核心论点。
- [x] **哪些证据可以跨模型共享？** **一切为质量服务**，优先共享以提升结果质量：提问中显式 `@` 引用的项目文本文件自动附带给 `text-only` API 目标和汇总模型，并在匿名汇总中附带各回答的证据画像（`askPolicy` + 实际工具调用）。
- [x] **一次决策值得花多少时间和额度？** **质量优先，同时压低无收益延迟与额度**：不加单独的“看后分流”LLM 阶段，不默认做 $N^2$ 互评辩论，通过单次自适应汇总、并行 fan-out 与零额外调用的上下文共享拿到最大质量收益。

### 落地进展（P0 & P1 已完成）

- **P0（下游一致性与证据底座）**：已修复 `historyAfter` 与 `selectPlan` 中的 `[ref:N]` 泄漏；`selectPlan` 自动提取 `## 最终答案` 避免将否决意见喂给执行器；`exec` 选定方案（忽略已取消实施）自动接续到后续追问历史；持久化 `RunResult.tools` 并在桌面端回显；汇总回退优先选择能读仓库的目标并记录 `fallback` / `preferredProvider` / `alsoAnswered`。

## 附录：与 Codex 独立回答的对比

**双方独立作答，核心结论一致，但参考的资料有重叠，一致不等于正确。** Codex 使用 gpt-6.2-astra、ultra 档、只读沙箱并开启联网搜索，用了约 9 万 token。发给它的只有原问题和项目背景，没有 Claude 的调研结论。

| 方面 | Codex 独有 | Claude 独有 |
| --- | --- | --- |
| 现状问题 | 用户选 B 实施后，历史仍沿用推荐 A 的汇总；各回答证据条件不同；decider 在看到回答前就做决定 | `[ref:N]` 带进历史和实施提示；汇总模型可能就是答题者之一 |
| 分歧处理 | 拆成事实分歧和偏好取舍；推荐时说明何时会反转 | 少数派正确的统计与「LLM 当裁判反而变差」的证据 |
| 融合还是选择 | 只引了支持融合的 Fusion-of-N | 补充了相反证据（When Agents Disagree、DeliberationBench），结论是有争议 |
| 评审偏差 | CodeJudgeBench 的判断随机性 | 作者标签偏差（EMNLP 2026）；自我偏好的重新评估（ICML 2026） |
| 反馈与路由 | 只列为待回答的问题 | 用历史记录估计模型可信度；PISA-E 动态路由 |
| 评估 | 离线对照方案和四个指标 | 增加「选择者强度」指标 |
